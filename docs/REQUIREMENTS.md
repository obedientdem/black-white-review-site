# 黑白测评组官网 V1.0 — Work / Sites / Codex 开发交接规范
版本：2026-10-16；状态：功能需求与视觉方向已经用户确认。此文件是开发时的唯一主要需求基线。不要再次要求用户回答已确认的设计选择。修改范围必须明确记录。

## 0. 产品目标
专业游戏测评媒体 + 玩家社区 + 发行商/独立开发者合作平台，ToC/ToB 兼顾。网站需要真实可运行的账号、后台、内容和活动业务，不能把静态页面或本地浏览器模拟数据称为 V1 完成。中文为主，界面完整中英双语，内容可仅有一种语言。

### 目标访问者与权限
- 游客：免登录阅读公开内容。
- 玩家：满18周岁方可注册；邮箱密码注册、邮箱验证、找回密码。允许收藏、游戏评分、提交评论（评论先审后显）、报名游戏测试、参与抽奖、查看状态；不允许投稿官方测评。
- 认证发行商：主动申请或管理员邀请，均由超级管理员认证；可编辑自己的活动草稿、提交活动待审、提交/查看商务合作申请及状态；只能访问属于自己的数据，不能改官方评分或查看全站招募者隐私信息。
- 内容编辑：撰写、编辑、发布官方测评和游戏资讯；不可控制用户/发行商认证、管理员账号或敏感设置。
- 超级管理员：用户和角色、认证、评论审核、活动审批、奖项与发奖记录、招募管理、商务进度、合作成绩、站点设置、内容管理全部权限。
- 权限必须在服务端/API/数据库访问层强制实施；前端隐藏按钮不足以实现权限控制。

## 1. 公开站点信息架构
主导航：首页 / 游戏测评 / 游戏资讯 / 活动中心 / 关于我们 / 商务合作；顶部提供中英切换、搜索、登录与个人中心；底部：联系方式、用户协议、隐私政策、活动规则、版权投诉入口等。
首页：品牌理念、100万+测评影响量与2000+累计测评（管理员维护，不应标注为实时自动数据）；精选测评；最近30天阅读量热门榜；官方高分推荐；近期游戏新闻；测试招募与抽奖；分众网络、合作成果、发行商入驻/合作入口。
测评列表：上方杂志式精选大图，下方规整卡片；游戏类型、平台、官方评分等筛选/排序；最近30天热门与高分分离。
测评详情：游戏原色大图 + 杂志标题 + 官方0—10分（0.5分步进）+ 白点/Pros与黑点/Cons（多条）摘要，再显示长篇图文、游戏资料、玩家独立评分、收藏和需要审核的评论；二者评分明确区分。
资讯：顶部头条大图 + 新闻列表；分类包括新游上线、版本更新、业界动态；资讯详情中英按内容可用语言展示。
活动中心：顶部精选活动专题 + 测试招募和网页抽奖双分区，明确开始/结束/开奖与状态；详情页有条件、规则和报名/参与入口。
商务合作：品牌宣言、分众触达与独立开发者零起步宣发价值、手动维护的指标、真实可公开案例、认证发行商入口、合作申请与联系信息。
关于我们：测评理念、团队介绍、旗下分众测评组和联系方式。

## 2. 测评/新闻内容管理
- 后台可创建游戏主档案，录入封面、开发者、发行商、发售日、类型、游戏平台/商店链接；同一游戏可对应多个平台；发布测评时选择测评平台与版本。
- 尽可能使用合规可用的多来源游戏资料接口（Steam、IGDB 等候选），先核实访问资质与使用条款；任何自动导入失败均可人工填写，不在未获许可情况下抓取；外部 API 接口以适配器隔离。
- 测评正文支持段落、图片、标题等富文本和作者、封面、发布时间、标签、链接、官方分数及黑白点；首批精选30—50篇历史测评，保留原文出处；不一次导入2000+篇。
- 资讯后台支持头图、标题、摘要、分类、正文、发布时间、发布状态。
- 全站UI有中文/英文；文章和新闻支持独立语言稿，可只提供中文或英文。切换到缺失语言时显示已存在原文并给出提示；同一测评的分数/浏览/评论是共享数据。V1不自动翻译。
- 近期热门：最近30天文章阅读次数排序，每日更新/按滚动窗口计算；不能拿累计浏览量假冒；高分推荐按官方评分排序，同分优先新文章。
- 数据指标100万+、2000+、分众组数、合作数量等由超级管理员手动维护，存数据口径与更新日期；不可用伪造统计。

## 3. 玩家互动
- 邮箱注册及验证、登录、登出、密码找回、账号设置；仅允许年满18岁的用户开通账号；具体年龄合规要求需在正式上线前审核，勾选声明不是身份核验。
- 玩家评分0—10（步进0.5），与官方评分独立显示；做好去重、频率限制、防刷基础措施。
- 玩家文字评论提交后为“待审核”，本人和管理员可查看；管理员批准后公开；拒绝/删除可记录状态及操作日志；支持处罚违规用户。
- 收藏测评、个人中心显示收藏/评分/评论审核状态/参与活动/报名状态。

## 4. 发行商与商务
- 发行商可申请入驻，也可受邀请；认证均需超级管理员审核。需填写公司/工作室、代表游戏、联系信息、必要证明。
- 发行商可以提交商务需求并跟踪待处理、洽谈中、已合作、未合作等状态；管理员可更新沟通记录；商业记录默认私有。公开合作案例必须人工挑选并确认公开授权。
- V1不做站内即时聊天、在线合同、支付或商业订单。

## 5. 活动、招募与抽奖
- 所有发行商活动先提交后审核，上架仅由管理员批准；管理员自己发布无需审核；退回可改稿再送审。活动包括测试招募和游戏抽奖。
- 测试招募：玩家报名 -> 仅测评组管理员查看、筛选 -> 在玩家适当授权后向发行商推荐 -> 管理状态。发行商无权限直接查看所有申请人的隐私信息。
- 抽奖：不同活动可配置地区、年龄、截止/开奖时间、自定义报名问题、奖品和中奖人数；邮箱验证后的每位账号每场最多报名一次；公平随机自动开奖，资格在截止时固定；日志可核验；防重复触发、并发与重复开奖，至少一次任务执行也不会多次发奖；失败可安全重试。网站公布适当脱敏的中奖结果、站内通知，管理员或发行商人工发奖并记录待发放/已发放状态；不自动存储/派发 Steam Key。
- V1不做平台外“关注/转发”任务自动验证。反作弊机制要标明能力边界：账号唯一不等于真实用户唯一。

## 6. 视觉规范（已确认12项）
- 整体A+C：黑白独立游戏杂志 + 适度实验性创意工作室感；不采用模板感浓的游戏商城视觉。
- 首页首屏：品牌宣言 + 核心影响力 + 重点测评，ToC/ToB均可快速进入。
- 黑白交替页面区域，游戏封面/截图保持原本彩色。
- Logo未来方向：黑白正负形 + 抽象游戏控制符号，适度不规则手作感；当前没有定稿，不可将草图当最终品牌资产。
- 字体：编辑式杂志标题 + 清楚易读的中英正文；少量手写批注/圈画用于评分和黑白点；不能全站手写体。
- 动效：静态为主，只有基础交互反馈，无大面积视差与鼠标跟随。
- 测评列表：精选杂志大图 + 实用卡片网格；测评详情：大图标题 + 官方评分 + 黑白点摘要 + 正文。
- 活动中心：大幅专题与招募/抽奖双分区。
- 商务页：品牌宣言 + 指标 + 真实案例；资讯：头条杂志 + 新闻列表。
- PC(约1440px)与移动端(约390px)必须可用；黑白对比度、正文可读性、性能优先。
- 游戏图片和合作品牌素材只使用自己拥有或有权使用的资源。演示内容需显式标注“示例”，不能冒充真实新闻/评分/合作成绩（尤其先前原型中的12+分众组数未核实）。

## 7. 法律合规与安全边界
- 用户协议、隐私政策、活动规则、版权投诉与下架流程、运营者联系方式要可见。不得以“非盈利学习”作为普遍侵权免责；不得以“最终解释权归本站”单方面剥夺法定权利。
- 收集报名者个人资料遵循最小必要、目的告知、授权及删除机制；保护未公开报名资料。上线前依运营地区核查隐私、活动、年龄及版权合规。
- 角色越权、邮箱验证、会话管理、CSRF/XSS/上传文件校验、限流、审计、数据库备份/恢复、秘密密钥保管等需测试；不可将管理员账号/真实密钥直接写进代码或公开页面。
- 开奖、审核、权限/年龄限制必须是真实后端机制，而不是按钮视觉效果或localStorage伪状态。

## 8. 第一版非目标
不批量迁移2000+历史测评；不AI翻译；不接入Steam/微信/QQ登录；不自动同步历史影响力统计；不自动发Steam Key；不提供社交任务自动验真；不让玩家投稿官方测评；不做全站IM聊天、付费/支付/合同；服务器/域名选择和正式部署地点暂缓。各种未来扩展留接口但不要预先实现。

## 9. 建议开发顺序与验收
P0: 适用工作环境技术可行性检查（Work/Sites是否能实现邮箱密码、数据库、角色权限、定时自动开奖、文件上传与图片展示）；如不满足，推荐Codex开发可迁移的独立全栈仓库，不要假装Sites有能力。提交明确技术决策，项目结构、实体关系、权限矩阵、安全风险、阶段任务清单。**P0阶段不开始大规模编码。**
P1: 设计系统 + 公开网页，使用清晰标识的演示数据；首页、测评列表/详情、新闻、活动中心、商务页，桌面/移动端验收。
P2: 真实账号、RBAC、后台内容CRUD、存储、双语与管理员发布流程；数据库持久化测试。
P3: 评论审批、评分与收藏、发行商入驻与商务流程、测试招募、抽奖与人工发奖；覆盖权限测试/定时幂等测试。
P4: 内容导入、真实数据替换、集成测试、安全审查、性能/无障碍、合规检查、上线前测试。
每阶段完成时应产生：变更文件概要、可访问预览/启动步骤、成功测试与未完成测试、已知问题、Git提交或可回滚版本、下一阶段首要任务。测试失败必须先修复，不能宣称完成。

## 10. 节省 token / 协作规约
1) 每次任务只完成一个阶段或一块闭环模块；优先修改现有文件，不要无故重构其他模块。
2) 项目代码与需求源放在持久化仓库/Work Site版本中；关键规则保存在此文件和短的进度文件 `PROGRESS.md`，每次只读相关文件+相关代码。不要把本需求每次重新粘贴到会话。
3) 每次只输出摘要：变更、测试结果、风险、阻塞，不输出大段完整源码或逐行思考。
4) 常规页面样式/文案修改用轻量步骤；账号权限、数据库迁移、开奖与数据泄露风险等使用较高推理力度并完整测试。
5) 同一功能优先选成熟稳定的库/服务；避免冗余抽象、未经要求的扩展、反复更换技术栈、无效设计探索。
6) 凡涉及付费接口、公开部署、域名/DNS、删除生产数据、发送真实邮件、访问真实用户信息，先取得用户明确批准。
7) 保存和版本化可还原的代码；版本恢复不代表数据库可以回滚，数据库迁移先备份并考虑回退。

## 11. P0 的明确完成标准
交付 (a) 面向非程序员的一页技术取舍结论：Sites 或独立代码仓库方案及原因；(b) 项目目录树和主要模块、(c) 关键数据实体与角色权限矩阵、(d) 5阶段开发任务，(e) 每阶段具体验收项目与风险。若某项能力无法在当前环境验证，明确标记“待验证”，不可猜测已可用。然后等待用户确认 P0，才正式进入 P1。
